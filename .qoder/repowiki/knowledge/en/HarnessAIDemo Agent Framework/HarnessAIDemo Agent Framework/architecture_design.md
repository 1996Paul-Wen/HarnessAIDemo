The harness package composes several subsystems around a single `HarnessConfig` dataclass (in `config.py`) that is consumed by every child module: `agent` owns the execution loop and orchestrator, `llm` provides the model backend selected by `LLMConfig`, `memory` supplies short/long-term/hybrid stores configured via `MemoryConfig`, `tools` registers callable capabilities discovered by the agent, `skill` loads markdown-defined capabilities into the tool registry, `session` isolates per-conversation state, `context` assembles system prompts + tool descriptions + memory into LLM messages, and `mcp` exposes a Model Context Protocol for external integration. The top-level `cli.py` entry point instantiates `HarnessConfig.default()`, builds the LLM engine, session manager, memory store, tool/skill registries, and finally an `Agent` or `Orchestrator` that ties them together; children communicate only through these shared config objects and explicit interfaces rather than direct cross-imports.
